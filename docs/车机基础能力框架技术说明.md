## 1. 这套框架解决什么问题

车机应用和普通手机应用最大的差别，不是界面，而是“数据和设备来源”。

普通应用通常只需要网络、数据库和手机系统 API；车机应用还会遇到：

- 车速、档位、温度、电量等车辆信号，可能来自 CAN、CarProperty、厂商广播；
- 诊断请求要走 CAN 多帧和 UDS 协议；
- 屏幕可能有多块，U 盘会热插拔，旋钮和方控是主要输入方式；
- 行车过程中需要限制视频、输入等交互；
- 不同车型、不同供应商的底层接口完全不一样。

`basic-vehicle` 的目标不是替代车机系统服务，而是把“应用侧经常要写、又容易写错”的部分封装成稳定的上层接口：

- 统一的 CAN/CAN FD 帧模型；
- SocketCAN 帧编解码和传输抽象；
- ISO-TP 多帧拆包/重组；
- UDS 诊断客户端；
- 统一的车辆信号模型和管理器；
- CAN、CarProperty、厂商广播三类信号源；
- 多屏、存储、亮灭屏、音频焦点、旋钮/焦点、驾驶限制等系统能力；
- 字节、校验、DBC、单位换算、配置和诊断日志等工具。

它不直接依赖 CarService、VHAL 或某个厂商 SDK。真正和系统/硬件打交道的地方，通过接口交给宿主接入，这样普通工程也能编译，车机工程再替换成真实实现。

一句话理解：

> `basic-vehicle` 是应用侧的车机能力适配层，不是车控服务本身。它负责把“原始帧/属性/广播”变成“应用能直接使用的信号和诊断结果”。

### 1.1 当前完成度

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 字节/位/校验/CRC | 已完成 | 纯 JVM，可直接单测 |
| CAN/CAN FD 帧与信号编解码 | 已完成 | Intel/Motorola、factor/offset、无效值、BRS |
| DBC 解析与查询 | 已完成 | 常用语句、扩展帧、枚举、注释、周期、一级 mux |
| SocketCAN 帧编解码与 fd 传输 | 已完成 | fd 由宿主/JNI 提供 |
| ISO-TP 单帧/多帧/流控 | 已完成 | 经典 CAN 与 CAN FD，最大 4095 字节 |
| UDS 诊断 | 已完成 | 会话、DID、DTC、安全访问、`0x78` |
| 统一信号管理 | 已完成 | CAN/CarProperty/广播/手动源、STALE |
| 多屏/存储/亮灭屏/焦点/音频 | 已完成 | 基于公开 Android API |
| 驾驶限制 | 已完成 | 未知车速默认锁定，可按车型覆盖 |
| 车型配置/诊断日志/单位换算 | 已完成 | MMKV、环形日志、常用量纲 |
| CAN 周期发送/发送队列 | 暂未封装 | 业务可用 `CanTransport.send` + 协程自行调度 |
| RTR/错误帧 | 不承载 | `CanFrame` 面向数据帧，错误/RTR 由驱动层处理 |
| 原生 `AF_CAN` socket 创建 | 宿主负责 | Android 公开 Java API 不提供，需 JNI/厂商服务 |
| CarPropertyManager 适配 | 宿主负责 | 通过 `CarPropertyClient` 接入，避免模块依赖 `android.car` |
| UDS 功能寻址、FD 32 位超长首帧 | 暂未实现 | 当前按物理寻址、最大 4095 字节 |

结论：应用侧不依赖车机系统的基础能力已经基本完整，CAN、DBC、ISO-TP、UDS、信号管理、系统能力都有可用的上层 API。剩余部分主要是两类：必须由宿主提供的平台边界（原生 CAN fd、CarPropertyManager 适配），以及明确标注的协议扩展（功能寻址、FD 超长首帧、嵌套 mux）。这些不会阻塞普通业务接入。

## 2. 车机基础概念速成

这一章面向没有车机经验的同学。已经熟悉 CAN 和 UDS 的读者可以跳到第 3 章。

### 2.1 CAN 和 CAN FD

**CAN** 是车辆内部最常见的总线。可以把总线理解成一条“广播通道”：多个 ECU（电子控制单元）挂在同一条线上，谁都可以发消息，但不是点对点发送。

一帧 CAN 报文主要包含：

| 概念 | 说明 |
| --- | --- |
| CAN ID | 报文的标识，也决定总线仲裁优先级。ID 越小，通常优先级越高 |
| 标准帧 | 11 位 ID，范围 `0x000..0x7FF` |
| 扩展帧 | 29 位 ID，范围 `0x00000000..0x1FFFFFFF` |
| 数据区 | 真正承载信号的字节 |
| DLC | 数据长度码。经典 CAN 最多 8 字节 |
| 周期 | 很多报文按固定周期发送，例如 20ms、100ms |

**CAN FD** 是 CAN 的扩展：

- 数据区最多 64 字节；
- 支持可变速率，数据段可以比仲裁段更快，这个能力叫 **BRS**（Bit Rate Switch）；
- 帧结构仍然是 CAN，但需要控制器和驱动都支持 FD。

框架里的 `CanFrame` 同时表示经典 CAN 和 CAN FD：

- `fd = false`：经典 CAN；
- `fd = true`：CAN FD；
- `bitRateSwitch = true`：CAN FD 开启 BRS；
- 经典 CAN 不允许 `bitRateSwitch = true`，构造时会校验。

### 2.2 DBC、报文和信号

CAN 帧的数据区是一串字节。应用真正关心的是“车速是多少”“档位是几档”，不是第 3 个字节的 bit 4 是什么。**DBC** 就是描述这层映射的文本文件。

DBC 里常见关键字：

| 关键字 | 含义 |
| --- | --- |
| `BO_` | 定义一条报文，例如 `BO_ 256 Powertrain: 8 ECU` |
| `SG_` | 定义报文里的一个信号 |
| `VAL_` | 定义枚举值，例如 3 表示 D 档 |
| `CM_` | 注释 |
| `BA_` | 属性，例如周期、起始值 |

一条信号通常包含：

- 名称；
- 起始位 `startBit`；
- 长度 `length`；
- 字节序（Intel/Motorola）；
- 是否有符号；
- `factor` 和 `offset`；
- 物理范围；
- 单位；
- 无效值；
- 枚举标签；
- 多路复用标识。

**原始值和物理值**：

```
物理值 = raw × factor + offset
```

例如 `raw = 605`、`factor = 0.1`、`offset = 0`，物理值就是 `60.5 km/h`。

**Intel 和 Motorola**：

- Intel（小端）：`startBit` 是信号最低位；
- Motorola（大端）：`startBit` 是信号最高位，跨字节时按 DBC 约定走位。

这是 DBC 解析最容易出错的地方，框架的 `ByteExt` 和 `CanSignalCodec` 已经按 DBC 规则处理。

**多路复用（Multiplexing）**：

同一位置在不同条件下表示不同信号，例如：

- `Mux = 0` 时，字节 1 表示车内温度；
- `Mux = 1` 时，字节 1 表示电池温度。

DBC 里通常写成 `M`（选择器）、`m0`/`m1`（分支信号）。`CanSignalSource` 支持一级多路复用；更复杂的嵌套多路复用需要扩展。

### 2.3 ISO-TP

UDS 诊断请求经常超过 8 字节，CAN 经典帧一帧装不下，于是需要 **ISO-TP（ISO 15765-2）** 把长数据拆成多帧。

四种帧：

| 帧类型 | 作用 |
| --- | --- |
| SF（Single Frame） | 单帧，负载较短 |
| FF（First Frame） | 首帧，告诉对方总长度和第一段数据 |
| CF（Consecutive Frame） | 连续帧，后续数据 |
| FC（Flow Control） | 流控，告诉对方能否继续发、一次发多少、间隔多久 |

流控里的两个关键参数：

- **Block Size**：发送方一次可以连续发多少帧，0 表示不限制；
- **STmin**：连续帧之间的最小间隔。

CAN FD 下单帧可以更长。ISO-TP 在 FD 里对超过 7 字节的单帧使用“转义长度”格式，框架已经处理。

框架的 `IsoTpChannel` 负责：

- 请求过长时拆成 FF + CF；
- 响应是 FF 时回 FC，并重组 CF；
- 处理 block size、STmin、padding；
- 处理超时和帧序号错误；
- 把多个诊断请求串行化，避免抢响应。

### 2.4 UDS

**UDS（ISO 14229）** 是统一诊断服务协议。可以把它理解成“向 ECU 提问和下发指令的标准语言”。

常见概念：

| 概念 | 说明 |
| --- | --- |
| SID | Service ID，服务号，例如 `0x22` 读数据、`0x2E` 写数据 |
| DID | Data Identifier，数据标识，例如 `0xF190` 通常用于 VIN |
| NRC | Negative Response Code，否定响应码，例如 `0x31` 请求超范围 |
| Session | 诊断会话，例如默认会话、扩展会话、编程会话 |
| Security Access | 安全访问，先要 seed，再算 key |
| DTC | Diagnostic Trouble Code，故障码 |
| `0x78` | Response Pending，ECU 表示“还在处理，请继续等” |
| Tester Present | `0x3E`，保持会话不超时 |

UDS 请求一般由测试端（Tester）发给 ECU，ECU 在另一个 CAN ID 上回复。框架用：

- `UdsClient` 表达服务；
- `UdsTransport` 抽象“怎么发、怎么收完整响应”；
- `IsoTpUdsTransport` 把 ISO-TP 通道接到 UDS 客户端；
- `0x78` 由传输适配层继续等待，最终响应再交给 `UdsClient`。

### 2.5 CarProperty 和厂商广播

除了 CAN，车机系统还可能通过两种方式提供车辆数据：

1. **CarProperty**：Android Automotive 的属性服务，按 `propertyId + areaId` 读写，例如车速、空调温度；
2. **厂商广播**：厂商服务发 `Intent`，通过 action 和 extras 携带数据。

本框架不直接依赖 `android.car`，而是定义 `CarPropertyClient` 适配接口；广播则提供 `BroadcastSignalSource`。这样：

- 普通工程可以正常编译；
- 车机工程用真实的 `CarPropertyManager` 实现适配器；
- 测试工程可以用假实现，不依赖车机环境。

### 2.6 信号质量、时间戳和 STALE

车辆信号不是“永远可信”的：

- 可能收到无效哨兵值，例如 `0xFFFF`；
- 可能超出物理范围；
- 可能一段时间没有更新；
- 可能还没收到第一帧。

框架用 `SignalQuality` 表示：

| 质量 | 含义 | UI 建议 |
| --- | --- | --- |
| `VALID` | 当前有效 | 正常显示 |
| `INVALID` | 无效值/超出范围 | 显示 `--` |
| `STALE` | 曾经有效，但超时未更新 | 显示 `--` 或“数据过期” |
| `UNKNOWN` | 尚未收到值 | 显示 `--` |

时间戳统一使用单调时钟 `monotonicMs()`，避免用户改系统时间导致超时判断错乱。

`VehicleSignalManager.observe(key, staleTimeoutMs = 300)` 会在超过 300ms 没有新值时补一条 `STALE`，UI 不需要自己写定时器。

### 3.4 两条典型数据流

**CAN 信号到 UI**：

```text
ECU 发帧
  → SocketCAN 驱动
  → SocketCanTransport.frames
  → CanSignalSource 按 DBC 解码
  → VehicleSignalManager 合并/超时
  → UI collect
```

**UDS 诊断**：

```text
UdsClient.readDataByIdentifier(0xF190)
  → IsoTpUdsTransport.request
  → IsoTpChannel.request
  → 拆 SF/FF/CF，等 FC
  → CanTransport.send
  → ECU 回复
  → IsoTpChannel 重组
  → UdsClient 解析 Negative / Success
```

### 3.5 线程与生命周期

- `SocketCanTransport` 在 `Dispatchers.IO` 上跑读循环；
- `IsoTpChannel` 默认在 IO 上收集响应，请求串行化；
- `CanSignalSource` 默认在自己的 `SupervisorJob + Dispatchers.Default` 里收帧；
- `BroadcastSignalSource` 在广播回调线程更新 `StateFlow`；
- `VehicleSignalManager` 不拥有线程，返回的 Flow 由收集方决定上下文；
- 所有持有监听/协程的类都实现 `Closeable`，页面销毁或模块退出时要关闭。

## 4. 各模块能力详解

### 4.1 协议基础工具

#### `ByteExt.kt`

提供裸字节和位操作：

- `u8At/i8At/u16At/i16At/u32At`：按字节下标取值；
- `bitAt/setBit`：按位读写；
- `extractBits`：按 DBC 规则提取位域；
- `extractSignedBits`：按补码取有符号值；
- `toBytesLe/toBytesBe`：数值转字节数组；
- `toHexString/hexToByteArray`：日志和调试用的 hex 转换；
- `concat`：拼接字节数组；
- `toBcdByte/bcdToIntOrNull`：BCD 时间、里程等。

示例：

```kotlin
val speedRaw = data.u16At(0)
val bit = data.bitAt(7)
val hex = data.toHexString()
```

需要注意：

- 位序号从 0 开始；
- Intel 和 Motorola 的 `startBit` 含义不同；
- 取位越界会抛 `IllegalArgumentException`，生产代码要保证数据长度。

#### `ChecksumExt.kt`

提供：

- 累加和 `checksumSum8`；
- 异或校验 `checksumXor8`；
- CRC8 SAE J1850 / ATM；
- CRC16 CCITT / Modbus；
- CRC32；
- 滚动计数器 `nextRollingCounter`。

这些校验只负责计算，不负责判断报文是否合法；业务需要按协议取正确范围。

### 4.2 CAN 模型与信号编解码

#### `CanFrame`

表示一帧 CAN/CAN FD 数据，不负责收发。

关键字段：

- `id`：报文 ID；
- `data`：数据字节；
- `extended`：是否扩展帧；
- `fd`：是否 CAN FD；
- `bitRateSwitch`：是否 BRS；
- `timestampMs`：接收时间戳。

常用方法：

```kotlin
val frame = CanFrame.standard(0x18F, ByteArray(8))
val value = frame.decode(spec)
val next = frame.write(spec, 60.5)
```

校验规则：

- 标准帧 ID 最大 `0x7FF`；
- 扩展帧 ID 最大 `0x1FFFFFFF`；
- 经典帧最多 8 字节；
- FD 最多 64 字节；
- BRS 只能用于 FD。

#### `CanSignalSpec`

描述一个信号，字段和 DBC 的 `SG_` 对应：

- `startBit`、`length`；
- `byteOrder`（Intel/Motorola）；
- `signed`；
- `factor`、`offset`；
- `unit`；
- `min/max`；
- `invalidRaw`；
- `valueLabels`。

`CanSignalSpec` 在构造时会校验长度、factor、范围等，DBC 解析出的非法值会在解析阶段修正并记录 issue。

#### `CanSignalCodec`

负责：

- 从 `CanFrame` 提取 raw；
- 补码转换；
- `physical = raw * factor + offset`；
- 无效哨兵判断；
- 物理范围判断；
- 物理值写回 raw 并限幅；
- `writeBits` 支持 Intel/Motorola。

解码结果 `CanSignalValue` 包含：

- `spec`、`raw`、`physical`；
- `quality`；
- `timestampMs`；
- `label`（枚举展示文本）；
- `display()`（上屏文本）。

#### `CanSignalValue.toSignalValue()`

把 CAN 专用结果转成通用 `SignalValue<Double>`，后续交给 `VehicleSignalManager`。

### 4.3 DBC 解析

#### `DbcParser`

解析：

- `BO_`：报文；
- `SG_`：信号；
- `VAL_`：枚举；
- `CM_`：注释；
- `BA_`：周期、起始值。

示例：

```kotlin
val db = DbcParser.parse(dbcText)
val message = db.message(0x100)
val speed = db.signal(0x100, "Speed")
```

特点：

- 解析失败的行不会中断整个文件，会记录到 `DbcDatabase.issues`；
- DBC 里的 `[0|0]` 通常表示未定义范围，解析时会当成不限制；
- `factor=0` 会被修正为 1.0 并记录 issue；
- 扩展帧通过 ID 的 bit31 拆出 `extended`；
- 支持一级 `M/m0/m1` 多路复用描述。

#### `DbcDatabase`

按 ID/名称查报文，按报文 + 信号名查信号。

#### `DbcMessage` / `DbcSignal`

`DbcMessage` 可以创建一帧并解码所有信号；`DbcSignal` 复用 `CanSignalSpec`，额外保存：

- `multiplexer`；
- `receivers`；
- `comment`；
- `startValueRaw`。

注意：`DbcMessage.decode(frame)` 会解出所有信号，不自动处理多路复用分支；需要多路复用语义时使用 `CanSignalSource`，它支持一级选择。

### 4.4 ISO-TP

#### `IsoTpConfig`

配置一条诊断通道：

```kotlin
IsoTpConfig(
    requestId = 0x7E0,
    responseId = 0x7E8,
    extended = false,
    fd = false,
    padding = 0x00,
    blockSize = 0,
    separationTimeMs = 0,
    timeoutMs = 1_000,
)
```

- `requestId`：测试端发给 ECU 的 ID；
- `responseId`：ECU 回复的 ID；
- `fd`：是否 CAN FD；
- `bitRateSwitch`：FD 是否 BRS；
- `padding`：填充字节，非空时经典帧补到 8 字节、FD 补到 64 字节；
- `blockSize`：本端接收连续帧时，每隔多少帧回一次 FC；
- `separationTimeMs`：本端流控里的 STmin。

#### `IsoTpCodec`

负责：

- SF/FF/CF/FC 编解码；
- CAN FD 单帧转义长度；
- STmin 字节与微秒换算；
- 帧类型判断。

它是纯 JVM 逻辑，适合直接写单元测试。

#### `IsoTpChannel`

负责一次完整的请求/响应交换：

```kotlin
val channel = IsoTpChannel(transport, IsoTpConfig(0x7E0, 0x7E8))
val response = channel.request(payload, timeoutMs = 1_000)
channel.close()
```

特性：

- 请求串行化；
- 请求多帧时等 ECU 的 FC；
- 响应多帧时向 ECU 回 FC；
- 支持 block size、STmin；
- 超时返回 `null`；
- 帧序号错误抛 `IsoTpException`；
- `keepWaiting` 回调可用于 UDS `0x78` 续等。

当前限制：

- 最大负载 4095 字节；
- 未实现 CAN FD 的 32 位超长首帧；
- 只实现物理寻址，不包含功能寻址。

### 4.5 UDS 诊断

#### `UdsClient`

已封装：

- `sessionControl`：`0x10` 会话控制；
- `readDataByIdentifier`：`0x22`；
- `writeDataByIdentifier`：`0x2E`；
- `testerPresent`：`0x3E`；
- `readDtcByStatusMask`：`0x19 02`；
- `securityAccess`：`0x27`，seed/key 通过回调传入；
- 通用 `request`。

返回值是 `UdsResult`：

- `Success`；
- `Negative`（含 NRC）；
- `Timeout`；
- `TransportError`。

`parseDtcByStatusMask` 可以把响应解析成 `UdsDtc`，并转换成 `P0301` 这样的故障码文本。

#### `IsoTpUdsTransport`

把 `IsoTpChannel` 接到 `UdsTransport`：

```kotlin
val client = IsoTpUdsTransport(channel).let { UdsClient(it) }
// 或
val client = channel.udsClient()
```

它会在收到 `7F SID 78` 时继续等待最终响应，而不是把 `0x78` 直接当失败返回。

### 4.6 CAN 传输层

#### `CanTransport`

统一接口：

```kotlin
interface CanTransport : Closeable {
    val frames: SharedFlow<CanFrame>
    suspend fun send(frame: CanFrame)
    override fun close()
}
```

它屏蔽：

- SocketCAN；
- 厂商 JNI/SDK；
- 其他 CAN 通道。

`frames` 是热流，只收订阅之后的数据。

#### `SocketCanTransport`

实现 SocketCAN 的帧读写：

```kotlin
val transport = SocketCanTransport.fromFileDescriptor(fd)
```

内部：

- 用 `SocketCanFrameCodec` 解析 `struct can_frame` / `struct canfd_frame`；
- 读循环持续发到 `frames`；
- 写操作串行化；
- `close()` 关闭 fd 并停止读协程。

注意：库不负责 `socket(AF_CAN)` 和 `bind`，需要 JNI 或厂商服务先打开 fd。CAN FD 还需要宿主给 socket 开启 `CAN_RAW_FD_FRAMES`。

#### `SocketCanFrameCodec`

支持：

- 经典帧 16 字节结构；
- CAN FD 72 字节结构；
- 标准帧/扩展帧；
- FD BRS；
- 过滤 RTR/错误帧（当前模型不承载）。

### 4.7 信号管理

#### `SignalValue<T>`

通用信号值：

```kotlin
data class SignalValue<T>(
    val value: T?,
    val quality: SignalQuality,
    val timestampMs: Long,
    val raw: Long? = null,
)
```

`map` 可以转换类型，同时保留质量和时间戳。

#### `SignalQuality`

- `VALID`：可用；
- `INVALID`：无效；
- `STALE`：过期；
- `UNKNOWN`：未知。

UI 建议只把 `VALID` 当正常值，其他显示 `--`。

#### `SignalSource`

所有数据源的统一接口：

```kotlin
interface SignalSource : Closeable {
    val name: String
    fun observe(key: String): Flow<SignalValue<*>>
    fun latest(key: String): SignalValue<*>?
    suspend fun write(key: String, value: Any): Boolean = false
    override fun close() {}
}
```

值类型由具体源决定，管理器通过泛型 `observe<T>` 交给调用方。

#### `VehicleSignalManager`

职责：

- 注册/注销多个信号源；
- 合并同一 key 的多个源；
- 按 key 返回 `Flow<SignalValue<T>>`；
- 可选超时补 `STALE`；
- 写入时按注册顺序反向尝试；
- 关闭时释放所有数据源。

```kotlin
val manager = VehicleSignalManager(defaultStaleTimeoutMs = 300)
manager.register(canSource)
manager.register(carPropertySource)

manager.observe<Double>("can:0x18F:Speed").collect { value ->
    // value.value 可能为 null
}
```

#### `CanSignalSource`

把 `CanTransport.frames` 按 DBC 解码成信号：

```kotlin
val source = CanSignalSource.fromDatabase(
    name = "can",
    transport = transport,
    database = db,
)

manager.register(source)
```

key 规则：

- 标准帧：`can:0x18F:Speed`；
- 扩展帧：`can:x0x18F:Speed`。

特点：

- 收到帧后只解命中报文的信号；
- 支持一级 DBC 多路复用；
- 写出时优先复用最近一帧，保留同帧其他信号位；
- 写多路复用分支信号前，调用方要先写选择器；
- 源只订阅 transport，不负责关闭 transport。

#### `CarPropertySignalSource`

不直接依赖 `android.car`。宿主实现 `CarPropertyClient`：

```kotlin
interface CarPropertyClient {
    fun subscribe(propertyId: Int, areaId: Int, callback: (CarPropertyReading) -> Unit): Closeable?
    fun get(propertyId: Int, areaId: Int): CarPropertyReading?
    fun set(propertyId: Int, areaId: Int, value: Any): Boolean
}
```

典型接入方式：

- `subscribe` 里调用 `CarPropertyManager.registerCallback`；
- `get` 里调用 `getProperty`；
- `set` 里调用 `setProperty`；
- 回调把 `CarPropertyValue` 转成 `CarPropertyReading`。

`CarPropertySignalSource` 负责把回调写入 `SignalValue`，并按 key 暴露 Flow。

#### `BroadcastSignalSource`

把厂商广播转成信号：

```kotlin
val source = BroadcastSignalSource(
    context = context,
    bindings = listOf(
        BroadcastSignalBinding(
            key = "vendor:ac_temp",
            action = "com.vendor.ACTION_AC_STATE",
            valueExtra = "temperature",
        ),
    ),
)
```

特点：

- 支持一个 action 多个信号；
- 支持 `qualityExtra` 和 `timestampExtra`；
- 复杂格式可以传 `converter` 自己解析；
- 默认按 exported 注册，接收系统/厂商广播；只接收应用内广播时传 not-exported 标志；
- 广播源只读。

#### `ManualSignalSource`

内存信号源，适合仿真和单测：

```kotlin
val source = ManualSignalSource("sim")
source.set("speed", 60.0)
manager.register(source)
```

新订阅者会立即收到最近一次值。

#### `SignalFlowExt`

- `onlyValid()`：过滤不可用值；
- `distinctByTolerance(tolerance)`：小抖动去重；
- `withStaleTimeout(timeoutMs)`：超时补 `STALE`。

| 类/文件 | 能力 | 用途 |
| --- | --- | --- |
| `AudioFocusExt` | 请求/释放音频焦点 | 导航、媒体播放前申请焦点 |

这是一个纯策略，不依赖信号来源，便于单测和按车型标定。

#### `AudioFocusExt`

```kotlin
val handle = context.requestAudioFocus(
    usage = AudioAttributes.USAGE_ASSISTANCE_NAVIGATION_GUIDANCE,

}
handle?.close()
```

返回 `null` 表示没有拿到焦点。

```kotlin
val displays = context.displayInfoList()

```

副屏的 density 可能和主屏不同，不要复用主屏的 `DisplayMetrics`。

```kotlin
val volumes = context.externalVolumes()
```

```kotlin
context.observeScreenState().collect { on -> ... }
```

只处理 AOSP 的 `SCREEN_ON/OFF`。ACC、READY 等车辆电源状态需要厂商信号，不能从这里获得。

## 5. 接入与使用

### 5.1 Gradle

`app` 已经依赖：

```gradle
implementation project(':basic-vehicle')
```

`basic-vehicle` 通过 `api project(':basic')` 获得协程、MMKV、AndroidX 等依赖，不需要在 `app` 重复声明版本。

### 5.2 接入 CAN

**第一步：拿到一个可用的 fd 或实现 `CanTransport`。**

Android 应用层没有公开的 `AF_CAN` socket API，通常由 JNI/厂商服务完成：

```kotlin
val fd: FileDescriptor = openCanSocketFromVendor("can0")
val transport = SocketCanTransport.fromFileDescriptor(fd)
```

如果厂商提供的是自己的 SDK，也可以直接实现 `CanTransport`，不需要用 SocketCAN。

**第二步：加载 DBC。**

```kotlin
val dbcText = assets.open("dbc/powertrain.dbc").bufferedReader().use { it.readText() }
val db = DbcParser.parse(dbcText)
```

**第三步：创建信号源和管理器。**

```kotlin
val manager = VehicleSignalManager(defaultStaleTimeoutMs = 300)
val canSource = CanSignalSource.fromDatabase(
    name = "can",
    transport = transport,
    database = db,
)
manager.register(canSource)
```

**第四步：订阅。**

```kotlin
lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        manager.observe<Double>("can:0x18F:Speed").collect { value ->
            val speed = value.value
            if (speed == null) {
                // 显示 "--" 或保留上次值
            } else {
                // 显示 speed km/h
            }
        }
    }
}
```

**第五步：退出时关闭。**

```kotlin
manager.close()   // 关闭 CanSignalSource
transport.close() // 关闭 fd
```

### 5.3 接入 UDS

```kotlin
val channel = IsoTpChannel(
    transport = transport,
    config = IsoTpConfig(
        requestId = 0x7E0,
        responseId = 0x7E8,
        timeoutMs = 2_000,
    ),
)
val client = channel.udsClient(defaultTimeoutMs = 2_000)

val result = client.readDataByIdentifier(0xF190)
when (result) {
    is UdsResult.Success -> {
        val vin = result.response.copyOfRange(3, result.response.size)
    }
    is UdsResult.Negative -> {
        // result.nrc
    }
    is UdsResult.Timeout -> {
        // 检查线束、ID、ISO-TP 参数
    }
    is UdsResult.TransportError -> {
        // 传输层异常
    }
}
```

切换会话、读 DTC、安全访问同理：

```kotlin
client.sessionControl(0x03)
client.readDtcByStatusMask(0xFF)
client.securityAccess(level = 0x01) { seed ->
    // 按车型算法生成 key
    key
}
```

`0x78` 由 `IsoTpUdsTransport` 自动续等；如果 ECU 处理时间较长，调用方要传更大的 `timeoutMs`。

### 5.4 接入 CarProperty

在车机工程中实现 `CarPropertyClient`：

```kotlin
class CarPropertyManagerClient(
    private val manager: CarPropertyManager,
) : CarPropertyClient {

    override fun subscribe(
        propertyId: Int,
        areaId: Int,
        callback: (CarPropertyReading) -> Unit,
    ): Closeable {
        val listener = object : CarPropertyManager.CarPropertyEventCallback {
            override fun onChangeEvent(value: CarPropertyValue<*>) {
                callback(
                    CarPropertyReading(
                        value = value.value,
                        timestampMs = monotonicMs(),
                    )
                )
            }

            override fun onErrorEvent(propertyId: Int, areaId: Int) {
                callback(
                    CarPropertyReading(
                        value = null,
                        quality = SignalQuality.INVALID,
                    )
                )
            }
        }
        manager.registerCallback(listener, propertyId, 10f)
        return Closeable { manager.unregisterCallback(listener) }
    }

    override fun get(propertyId: Int, areaId: Int): CarPropertyReading? {
        val value = manager.getProperty<Any>(propertyId, areaId)
        return CarPropertyReading(value.value)
    }

    override fun set(propertyId: Int, areaId: Int, value: Any): Boolean {
        // 示意：实际使用按属性类型传入对应 Class
        manager.setProperty(Any::class.java, propertyId, areaId, value)
        return true
    }
}
```

实际代码中的 `setProperty` 泛型写法要按车型 SDK/API 版本调整；这份适配器的职责只是把 `CarPropertyManager` 的差异挡在框架外。

### 5.5 接入厂商广播

```kotlin
val source = BroadcastSignalSource(
    context = context,
    bindings = listOf(
        BroadcastSignalBinding(
            key = "vendor:gear",
```

没有真实 CAN 时，用 `ManualSignalSource`：

- 音频焦点：播放前 `requestAudioFocus`，结束时 `close`；

## 7. 设计边界与限制

### 7.1 为什么不直接依赖 CarService/VHAL

`basic-vehicle` 是普通 Android library，目标是让非车机工程也能编译。直接依赖 `android.car` 会导致：

- 普通手机工程无法编译；
- 不同车机 SDK 版本差异大；
- 单元测试必须跑在车机环境。

因此：

- SocketCAN 只负责 fd 之上的帧编解码和读写；
- CarProperty 只定义 `CarPropertyClient` 接口；
- UDS 只依赖 `CanTransport`；
- 厂商广播用标准 `BroadcastReceiver`。

### 7.2 CAN FD

- `CanFrame.fd=true` 时数据最长 64 字节；
- 需要宿主开启 `CAN_RAW_FD_FRAMES`；
- BRS 只是帧标记，实际速率由控制器和驱动配置决定；
- 当前 `CanFrame` 不承载 RTR/错误帧。

### 7.3 ISO-TP

- 最大 4095 字节；
- 未实现 FD 32 位超长首帧；
- 只支持物理寻址；
- `0x78` 续等仍受本次请求总超时限制；
- FC 的 block size/STmin 已实现，但极端 ECU 的非标准流控需要按车型适配。

### 7.4 DBC

- 支持常用 `BO_/SG_/VAL_/CM_/BA_`；
- 不支持所有 DBC 扩展语句；
- 支持一级多路复用，嵌套多路复用需要业务扩展；
- `DbcMessage.decode` 会解所有信号，多路复用语义请用 `CanSignalSource`。

### 7.5 广播

- 默认按 `RECEIVER_EXPORTED` 注册，以接收系统/厂商广播；
- 只接收应用内广播时传 not-exported 标志；
- 广播内容没有统一标准，必须按厂商协议配置 `action` 和 extras；
- 导出的动态接收器存在被伪造广播影响的风险，必要时增加权限或校验字段。

### 7.6 信号时间

- 统一使用 `monotonicMs()`；
- 如果宿主自己传时间戳，必须保持同一时钟基准；
- `SignalValue.timestampMs` 不是墙钟，不要直接格式化成日期。

### 7.7 性能

- CAN 帧解码是轻量纯逻辑，主要成本在每帧多次位操作；
- 高频报文建议只绑定需要的信号；
- `CanSignalSource` 按报文分组，不会对每帧遍历全部 DBC；
- 日志不要在高频循环里打 VERBOSE；
- 帧流是热流，订阅前收到的数据不会补发。

## 8. 常见问题排查

### 8.1 收不到 CAN 帧

检查：

1. fd 是否已经 bind 到正确的 `canX`；
2. CAN FD 是否开启 `CAN_RAW_FD_FRAMES`；
3. 波特率/采样点是否匹配；
4. `SocketCanTransport` 是否已经 `close`；
5. 是否有其他进程独占 fd；
6. 订阅是否在启动读循环之后。

### 8.2 信号一直是 `STALE`

可能原因：

- 报文周期大于 `staleTimeoutMs`；
- 报文 ID 或扩展帧标志配错；
- DBC 信号位定义错；
- 多路复用选择器没有匹配；
- 源已经关闭但 UI 还在收集旧值。

### 8.3 UDS 超时

按顺序检查：

1. 请求/响应 ID 是否成对；
2. 波特率、ISO-TP 参数；
3. 是否需要先切换扩展会话；
4. ECU 是否返回 `0x78`，总超时是否太短；
5. CAN FD 单帧长度/转义格式；
6. 响应是否为多帧但 FC 参数不匹配。

### 8.4 UDS 返回 NRC

常见 NRC：

- `0x11`：服务不支持；
- `0x12`：子功能不支持；
- `0x13`：长度错误；
- `0x22`：条件不满足；
- `0x31`：超出范围；
- `0x33`：安全访问被拒；
- `0x35`：key 无效；
- `0x78`：还在处理。

`0x78` 正常应由传输层继续等，不应直接展示成失败。

### 8.5 CarProperty 没有数据

- 宿主是否真的实现了 `CarPropertyClient`；
- `propertyId/areaId` 是否正确；
- 是否有对应权限；
- `registerCallback` 的频率是否太低；
- `get` 和回调是否把 `CarPropertyValue` 转成了 `CarPropertyReading`。

### 8.6 多屏尺寸不对

- 使用 `displayContext(displayId)`，不要复用 Activity 的 metrics；
- 副屏 density 可能不同；
- `getRealMetrics` 取的是真实显示区域，和可用窗口区域可能不同。

### 8.7 U 盘列表为空

- 应用是否有存储权限；
- 卷是否已挂载；
- 部分车型的 U 盘路径不在标准 external files 目录下；
- Android 10+ 分区存储会限制直接路径访问，优先使用 `content://` 或 SAF。

### 8.8 音频焦点拿不到

- 是否被电话/导航占用；
- `usage`/`contentType` 是否合适；
- 是否在播放结束后忘记 `close`；
- 某些车机要求使用特定 stream type。

## 11. 一页接入检查清单

- [ ] `app` 已依赖 `basic-vehicle`；
- [ ] CAN fd 已由 JNI/厂商服务打开并 bind；
- [ ] CAN FD 已开启 `CAN_RAW_FD_FRAMES`；
- [ ] DBC 文件已加载，`issues` 已检查；
- [ ] 信号 key 使用 `can:0x...:Signal` 规则；
- [ ] 多路复用信号已配置选择器；
- [ ] `VehicleSignalManager` 设置了合适的 `staleTimeoutMs`；
- [ ] UDS 请求/响应 ID 成对；
- [ ] `0x78` 场景设置了足够的超时；
- [ ] CarProperty 适配器实现了 `subscribe/get/set`；
- [ ] 广播源注册标志和权限符合车机安全要求；
- [ ] 页面/模块销毁时关闭 `manager`、`transport`、`channel`；
- [ ] 车速异常时按 `DrivingRestriction` 的默认锁定策略处理；
- [ ] 高频信号没有在 UI 线程做重计算或打大量日志。
